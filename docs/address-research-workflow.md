# Поиск и подтверждение адресов в A2WC012E

Этот документ фиксирует практический процесс, которым в проекте ищутся новые таблицы, оси, code hooks и RAM-параметры. Цель — отделять **найденный кандидат** от **адреса, безопасного для прямой правки BIN**.

## 1. Начинать только с полного ROM

Базовая проверка перед любым поиском:

```text
Размер:      524288 bytes
Internal ID: A2WC012E @ 0x2000
```

Для одного из контрольных полных BIN проекта:

```text
File:    forester_sg9_sti_v2 (1).bin
SHA-256: 50cbcb183775b10f75a4c12022842647bc036a078f991aec2629b084fd6af82a
```

Урезанный dump или файл с нулевой калибровочной областью нельзя использовать для подтверждения offsets.

## 2. Источники кандидатов

Адрес может появиться из нескольких источников:

1. близкого RomRaider definition;
2. кастомного A2WC012E XML;
3. соседней уже подтверждённой таблицы;
4. структуры осей и характерных значений непосредственно в BIN;
5. исходников/target header MerpMod;
6. binary diff между двумя известными ROM.

Сам факт появления адреса в XML или header **не делает его CONFIRMED**.

## 3. Разделять пространства адресов

В проекте встречаются разные типы адресов, их нельзя смешивать:

```text
0x000xxxxx   ROM / code / calibration address
0xFFFFxxxx   runtime RAM pointer
0x8000xxxx   область метаданных/patch runtime image MerpMod
```

Например, `0x589B0` — адрес калибровочного scalar в ROM, а `0xFFFFB218` — runtime RAM-переменная Engine Speed. Это разные сущности и разные способы проверки.

## 4. Поиск по соседству

Очень полезный приём — исследовать область вокруг уже известной таблицы.

Пример проекта:

```text
Base Timing Idle A: 0x5B157
ECT axis:           0x5AFDC
```

Первая таблица содержит 16 однобайтовых точек. Следующие 16 байт по адресу `0x5B167` также образуют правдоподобную ECT-зависимую idle timing table с той же осью.

Так была обнаружена вторая таблица:

```text
Base Timing Idle B: 0x5B167
ECT axis:           0x5AFDC
Points:             16
```

**Наличие и структура таблицы подтверждены.** Семантика переключения A/B, в том числе связь с TGV или режимом In-Gear, пока считается отдельной гипотезой.

## 5. Проверка datatype / endian / scaling

Для каждого кандидата нужно проверить:

- тип данных (`uint8`, `uint16`, `float` и т.д.);
- endian;
- размерность;
- длину осей;
- scaling expression;
- физически правдоподобный диапазон значений;
- соответствие тому, что отображает RomRaider.

Если адрес даёт «красивое» число только при случайно выбранном scaling, это не подтверждение.

## 6. Shared axes — сильный сигнал, но не доказательство назначения

Subaru часто переиспользует одну ось для нескольких соседних таблиц. Если две области одинаковой длины и обе корректно декодируются по общей оси, это повышает доверие к найденной структуре.

Однако название таблицы и условие её выбора ECU всё равно нужно подтверждать отдельно.

## 7. Контрольная правка одной ячейки

Самый надёжный способ перевести адрес из `PROBABLE` в `CONFIRMED`:

1. сохранить исходный полный BIN;
2. через definition/editor изменить **одну** тестовую ячейку;
3. сохранить копию;
4. сделать binary diff;
5. проверить точный изменившийся offset;
6. убедиться, что не изменились посторонние байты, кроме ожидаемого checksum/служебной области;
7. вернуть исходное значение, если это была только адресная проверка.

Именно так была подтверждена MAF Scaling: изменения оказались только в ожидаемой MAF Flow table.

## 8. Проверка таблицы целиком

Для 2D/3D таблицы отдельно фиксировать:

```text
data address
X axis address
Y axis address
sizex / sizey
storagetype
endian
scaling
```

Нельзя подтверждать только `data address`, если оси или размерность ещё неизвестны.

## 9. Как использовать MerpMod target map

`Targets/A2WC012E.h` — очень ценный источник для поиска code hooks и RAM addresses. Но это **source-derived reference map**, а не автоматическое доказательство того, что каждое имя и назначение верно для нашей текущей сборки.

Использование:

1. взять адрес из target header;
2. проверить, что он относится именно к `A2WC012E`;
3. сопоставить с ROM/дизассемблированным кодом или runtime-наблюдением;
4. только после этого повышать статус.

Отдельная карта вынесена в [`merpmod-a2wc012e-address-map.md`](merpmod-a2wc012e-address-map.md).

## 10. Статусы адресов

- ✅ **CONFIRMED** — структура/offset подтверждены непосредственно на A2WC012E и при необходимости diff.
- 🟡 **PROBABLE** — сильное совпадение по definition, соседству или структуре, но независимой проверки недостаточно.
- 🧪 **EXPERIMENTAL** — адрес используется в тестовой работе/patch и ещё проверяется на машине.
- 📚 **REFERENCE** — адрес получен из исходников/target map и служит ориентиром для reverse engineering.
- ❌ **REJECTED / DO NOT PATCH** — конкретная идентификация или правка дала проблему либо была опровергнута.

## 11. Что обязательно записывать вместе с новым адресом

Для каждого нового результата фиксировать:

```text
ROM ID
исходный BIN + SHA-256
адрес
тип адреса: ROM / code / RAM
размер и datatype
ось/оси
scaling
источник кандидата
способ проверки
статус
связанный тестовый ROM/log
```

## Главное правило

> Сначала доказать, что мы понимаем байты, и только потом их менять.

Если адрес найден только по чужому XML, похожему ROM или названию из исходников — это карта для поиска, а не готовый binary patch.
