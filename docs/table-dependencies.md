# Связи таблиц и параметров

Цель этого файла — отвечать на вопрос: **если правим одну таблицу, что ещё обязательно проверить?**

Это не означает, что связанные таблицы всегда нужно менять. Сначала их нужно проверить по логам и понять, участвуют ли они в текущем режиме.

## Короткая карта зависимостей

| Что меняем | Что обязательно проверить | Что обычно НЕ стоит менять одновременно без причины |
|---|---|---|
| MAF Scaling | MAF g/s, Engine Load, trims, CL/OL, WB AFR, выбранные fueling/ignition cells | Injector scalar, ignition |
| Injector Scalar | latency, trims, MAF, OL AFR, pulse width | MAF Scaling «для компенсации» |
| Injector Latency | напряжение, ХХ, low pulse width, trims | scalar без подтверждения |
| Primary OL Fueling | WB AFR, Final Fueling Base, learning, IAT/ECT comp, load/RPM | MAF только по разнице WB vs Primary OL |
| A/F Learning ranges | фактический learning bucket, CL→OL, сохранение learning | MAF/форсунки без отдельной причины |
| Ignition | IAM, FBKC, FLKC, AFR, IAT, ECT, load/RPM | крупные fueling-изменения в том же тесте |
| TGV delete | DTC, запуск, ХХ, переходные режимы | неизвестные TGV tables «на всякий случай» |
| Idle catch | RPM, throttle, airflow/load, AFR/trims, ignition, load compensation | MAF/injectors без отдельного симптома |
| Airflow/load limits | load, torque, throttle, definition/offset, diff | прямой hex patch без подтверждения |

---

## MAF Sensor Scaling

**Изменяем:**
- MAF Sensor Scaling.

**Проверяем одновременно:**
- MAF Voltage;
- MAF g/s;
- Engine Load;
- A/F Correction #1;
- A/F Learning #1;
- Closed Loop / Open Loop status;
- Wideband AFR в OL;
- Final Fueling Base / итоговую цель смеси, если параметр доступен;
- какие load/RPM ячейки fueling и ignition выбирает ECU после изменения MAF.

**Связи:**
- ошибка MAF влияет на расчёт нагрузки;
- нагрузка влияет на выбор ячеек fueling и ignition;
- поэтому неверный MAF нельзя рассматривать только как «ошибку смеси».

**Практическое правило:**
если корректируется MAF, не нужно одновременно «подгонять» injector scalar только потому, что trims ещё не идеальны. Сначала нужно понять, какая часть ошибки действительно относится к измерению воздуха.

## Injector Flow Scaling

**Изменяем:**
- Injector Flow Scaling / Injector Scalar.

**Обязательно проверить:**
- Injector Latency;
- A/F Correction;
- A/F Learning;
- AFR на ХХ и cruise;
- AFR в OL;
- MAF Scaling;
- injector pulse width, если параметр доступен.

**Важно:**
Если MAF ещё содержит систематическую ошибку, коррекция injector scalar может просто замаскировать её.

Изменение scalar глобально влияет на расчёт топлива, поэтому после него нужно повторно проверить как CL, так и OL.

## Injector Latency

**Изменяем:**
- Injector Latency по напряжению.

**Проверяем:**
- AFR/trims на ХХ;
- AFR/trims при малом pulse width;
- напряжение бортовой сети;
- поведение trims при изменении нагрузки;
- scalar форсунок.

Если ошибка сильнее на малых импульсах, а под нагрузкой уменьшается, latency становится более вероятной причиной, чем scalar.

## Primary Open Loop Fueling

**Изменяем:**
- Primary Open Loop Fueling.

**Проверяем:**
- фактический Wideband AFR;
- Final Fueling Base / итоговую цель;
- A/F Learning, если она сохраняет влияние в данном режиме/ROM;
- температурные компенсации;
- enrichment/transition compensation;
- Engine Load и RPM, чтобы убедиться в правильной выбранной ячейке;
- факт и момент перехода CL → OL.

**Не делать:**
Не сравнивать WB AFR только с числом из Primary OL и сразу считать разницу ошибкой MAF.

Если итоговая цель ECU отличается от Primary OL из-за компенсаций, MAF нельзя корректировать по неправильной базе сравнения.

## A/F Learning ranges

**Изменяем:**
- границы диапазонов A/B/C/D либо разрешение обучения.

**Проверяем:**
- в каком диапазоне реально накапливается learning;
- остаётся ли эта коррекция при переходе в OL;
- не маскирует ли learning ошибку MAF или injector scaling;
- изменилось ли только место хранения коррекции или реально её влияние на fueling.

Изменение границы диапазона само по себе не гарантирует исчезновения нежелательной коррекции.

В проекте уже проверялся перенос нижней границы D примерно `60 → 40 g/s`; как самостоятельное решение он ожидаемого эффекта не дал. См. `rejected-experiments.md`.

## Ignition tables

**Изменяем:**
- Base Timing / Advance-related таблицы.

**Проверяем:**
- IAM;
- FBKC;
- FLKC;
- Engine Load;
- RPM;
- AFR;
- IAT;
- ECT;
- итоговый фактический ignition timing, если логируется.

После изменения fueling зажигание нужно оценить повторно, даже если timing tables не менялись.

При диагностике лучше не вносить одновременно крупное изменение AFR и крупное изменение timing: иначе сложнее понять причину изменения knock-поведения.

## Boost / Target Boost

**Изменяем:**
- Target Boost и/или связанные compensation tables.

**Проверяем:**
- фактический boost;
- wastegate duty;
- атмосферное давление;
- Target Boost Compensation (Atm. Pressure);
- multiplier/offset, если они используются данным ROM;
- AFR;
- knock;
- load limits.

## TGV delete

**Изменяем/отключаем:**
- DTC, относящиеся к отсутствующим TGV motor/sensor цепям.

**Проверяем:**
- отсутствие новых DTC;
- запуск и ХХ;
- переходные режимы;
- наличие дополнительных TGV compensation tables в definition/ROM.

Отключение DTC не доказывает автоматически, что все связанные с TGV калибровки можно оставить без проверки.

Но и обратное тоже верно: **не нужно занулять или менять неизвестные TGV-related таблицы просто «на всякий случай»**, если нет данных, что они реально мешают после удаления hardware.

## Idle catch / стабилизация ХХ после сброса газа

Если правится логика подхвата оборотов при закрытии дросселя или стабилизация ХХ, проверить в одном логе:

- RPM и скорость падения оборотов;
- Throttle Opening Angle / Target Throttle, если доступны;
- MAF g/s;
- Engine Load;
- A/F Correction / Learning;
- AFR;
- ignition timing;
- ECT / IAT;
- нагрузки кондиционера/генератора/ГУР, если они участвуют в тесте;
- целевой idle RPM и связанные компенсации, если доступны в definition.

**Важно:**
проблему idle catch не следует автоматически лечить MAF Scaling или injector scalar, если в стабильном ХХ и cruise топливные коррекции уже нормальны. Сначала нужно отделить топливную ошибку от собственно idle/throttle control.

После правки обязательно проверить не только один сброс газа, а несколько сценариев:

- сброс с небольших оборотов;
- сброс с более высоких оборотов;
- остановка автомобиля;
- горячий ХХ;
- включение дополнительной нагрузки, если она влияет на симптом.

## Airflow / load limits

Если меняется ограничение airflow/load или параметр, который предположительно ограничивает расчётный поток/нагрузку, дополнительно проверить:

- Engine Load до и после изменения;
- MAF g/s и MAF Voltage;
- throttle target / actual;
- Requested Torque / torque-related tables;
- связанные load limits;
- fueling/ignition cell selection;
- отсутствие переполнения/неожиданного выхода за оси таблиц.

Для A2WC012E уже был неудачный эксперимент с прямой правкой области airflow limit без достаточно подтверждённого определения: конкретная сборка вызвала троение и отсутствие нормальной реакции на педаль. Поэтому такие правки нельзя повторять по предположительному offset.

## Прямая правка BIN без definition

Если нужная таблица отсутствует в definition:

1. найти адрес и структуру таблицы;
2. подтвердить адрес по корректному definition/сигнатурам/соседним данным;
3. проверить datatype, endian, scale и размер;
4. изменить только ожидаемые байты;
5. сделать binary diff;
6. проверить checksum, если применимо;
7. проверить, что diff не затронул соседние данные;
8. только после этого тестировать ROM.

Прямая запись по предположительному offset без проверки — запрещённый для stable workflow подход.

## Главное правило зависимостей

**Связанную таблицу нужно обязательно проверить, но не обязательно менять.**

Чем больше таблиц изменено одновременно, тем меньше диагностическая ценность следующего лога.
