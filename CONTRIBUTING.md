# Как вносить изменения в проект

Этот репозиторий рассчитан на совместную работу, но при калибровке ECU важнее всего сохранить происхождение каждой версии и возможность безопасно откатиться назад.

## Перед изменением ROM

Сначала ответить на пять вопросов:

1. Какую наблюдаемую проблему решаем?
2. Какая таблица или группа таблиц считается основной причиной?
3. Какие связанные параметры нужно проверить по `docs/table-dependencies.md`?
4. Какой результат ожидается увидеть в логе?
5. Какая предыдущая ROM является заведомо рабочей точкой отката?

Если на эти вопросы нет ответа, ROM пока лучше не менять.

## Правило изменения

По возможности одна версия должна содержать одну логическую группу изменений.

Хорошо:

```text
v37 — idle catch only
```

Плохо:

```text
v37 — MAF + injector scalar + OL fueling + ignition + idle
```

Чем меньше независимых изменений, тем проще понять результат теста.

## Что делать с BIN

- исходный BIN не перезаписывать;
- исторический filename не менять задним числом;
- новый BIN сохранять отдельной версией;
- перед прошивкой сравнить его с базой через binary diff;
- для прямых hex/BIN-правок отдельно подтвердить offset, datatype, endian, scale и размер;
- experimental ROM нельзя считать stable только потому, что двигатель запустился.

Рекомендуемое размещение:

```text
roms/stock/
roms/stable/
roms/experimental/
roms/rejected/
```

## Что обязательно записать после теста

В `CHANGELOG.md`:

```text
Base ROM:
Изменённые таблицы:
Причина:
Ожидаемый результат:
Фактический результат:
Лог:
Статус:
```

Если тест неудачный — дополнительно записать его в `docs/rejected-experiments.md`.

Неудачную сборку не нужно скрывать: корректно задокументированный rejected ROM полезен тем, что не даёт повторить ту же ошибку.

## Когда ROM можно считать stable

Минимально должны быть выполнены условия:

- нормальный запуск;
- нормальная реакция на педаль;
- устойчивый ХХ;
- нет новых критичных DTC;
- значения MAF / load / AFR выглядят логично;
- проверены IAM / FBKC / FLKC для соответствующего режима;
- есть лог нужного режима;
- известен diff относительно базы;
- результат соответствует цели изменения.

## Совместная работа через GitHub

Если репозиторием пользуются несколько человек, предпочтительно:

1. не переписывать историю уже опубликованных версий;
2. делать понятные commit messages;
3. для спорных или крупных изменений использовать отдельную ветку / Pull Request;
4. в PR описывать не только «что поменялось», но и почему;
5. не помечать гипотезу как CONFIRMED без проверки на автомобиле или достаточных данных.

## Уровни уверенности

- `CONFIRMED` — подтверждено тестом/логом/diff;
- `PROBABLE` — хорошо обосновано, но проверки ещё недостаточно;
- `EXPERIMENTAL` — находится в тесте;
- `REJECTED` — конкретный метод или ROM дал плохой результат.

Главное правило: **не формулировать причинно-следственную связь жёстче, чем позволяют данные.**
